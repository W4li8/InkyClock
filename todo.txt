[2026-09-27 12:18] State-machine gap review (none fixed yet -- design
  decisions needed, not obvious bugs -- flagging here for later):

  1. No ringing timeout. If MODE_RINGING is never dismissed, buzzer.
     play_alarm_tune() and the border flash run forever, and
     time_sync.poll() stays paused the whole time (explicitly skipped
     during MODE_RINGING so a resync can't delay dismissal). No "give up
     after N minutes" exists.

  2. No persistence across reboot/power-loss. Alarm() is a fresh instance
     every main() run -- a crash or power cycle silently resets
     hour/minute/enabled back to config.DEFAULT_ALARM_HOUR/MINUTE
     (7:00, enabled=True), discarding whatever the user actually set, with
     no indication anything changed. Doesn't need extra hardware to fix --
     the Pico's onboard 2MB QSPI flash already hosts the MicroPython
     filesystem (same flash main.py lives on); persisting just means
     writing a small state file (e.g. one-line JSON: hour/minute/enabled)
     on actual change (exit_edit, toggle_enabled) and reading it back at
     boot with a try/except fallback to config defaults if missing/corrupt
     (first boot, or a write interrupted mid-write). Flash write endurance
     (~100k erases/sector, wear-levelled by the filesystem) is a non-issue
     at alarm-editing frequency.

  3. Resync can jump forward across the alarm's exact target minute.
     check_ring() needs an exact (hh, mm) match with no memory of "did I
     already pass this" -- if a scheduled or boot resync corrects the RTC
     forward across the alarm's minute (e.g. 6:58 -> corrected to 7:03),
     that day's alarm is silently skipped. Same failure family as #4
     below, different trigger (a resync jump instead of user interaction).

  4. check_ring() only runs in MODE_CLOCK -- already known re: MODE_EDIT
     (up to ALARM_EDIT_TIMEOUT_S+ exposure), but also applies to
     MODE_PREVIEW (much smaller, max ~3s exposure) which wasn't previously
     called out explicitly.

  Minor, not really "gaps": a resync due on the exact same tick as the
  alarm firing delays ring start by a few seconds (time_sync.poll() runs
  first in the loop each iteration) -- latency, not a miss. RTC weekday
  auto-increment between resyncs is trusted hardware behavior, not
  independently verified -- self-corrects within 4h regardless if wrong.

[2026-10-02 23:30] Decided against (not just deferred) the battery-backed
  RTC and UPS hardware ideas from idea.txt, per user request.

  Reasoning, with numbers, now in docs/time-accuracy-decision.md: crystal
  drift between 4h syncs is sub-2-second even over a full day of entirely
  failed syncs, and sub-2-minute even over a full week of them -- nowhere
  close to the stated 10-min alarm-miss budget. The only real risk is an
  actual power outage, and that's already bounded by two things built
  this session: boot-time resync-before-anything-else, and persist.py's
  10-min flash checkpoint (built specifically to hit this exact target).
  A UPS only helps through outages long enough that the home router/modem
  would be down too anyway (making Wi-Fi resync moot regardless of Pico
  power); an RTC would only improve on a 10-min target already met.
  idea.txt's RTC/UPS bullets replaced with a pointer to the decision doc;
  docs/README.md indexed.
