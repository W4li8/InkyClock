InkyClock - future ideas / nice-to-haves (not scheduled, just parking lot)

- Temperature sensor (e.g. a cheap I2C one like a BME280/SHT31) to auto-control
  the A/C, and auto-control blinds based on time of day. Would need a relay/
  IR-blaster or similar actuator for the A/C side and a motor or existing
  smart-blinds API for the blinds side -- bigger scope than the clock itself,
  parking here for later.
  Confirmed on the actual board: the RP2350's built-in temp sensor
  (machine.ADC(4)) works fine on this firmware (was briefly a known
  MicroPython/RP2350 bug elsewhere, not an issue here) and reads live, but
  it measures die temperature, not room temperature -- read 32.7C sitting on
  a desk, heated by the CPU/USB regulator, with an offset that drifts with
  board activity. Not usable for this idea; a real external I2C sensor
  (BME280/SHT31) is still the right call.

- Battery-backed external RTC module (DS3231 / PCF8523, I2C, coin-cell).
  The Pico has no battery-backed RTC (see conversation) -- it resets on
  every power loss and only gets corrected again once wifi.TimeSync
  succeeds. An external RTC would survive outages and give a sane baseline
  immediately at boot even before/without a successful Wi-Fi sync.
  Prefer PCF8523 over DS3231 -- lower backup current, and most PCF8523
  breakout boards skip the trickle-charge circuit that some cheap DS3231
  boards wire in for a rechargeable cell (which degrades/damages a normal
  non-rechargeable CR2032 if left in place -- check for it either way).
  Whichever chip: expect to swap the CR2032 every 5-10 years -- that's the
  battery's own shelf life, not something the RTC's ~1-3uA draw limits.
  Note: this is unrelated to (and not a fix for) the lightsleep/RTC-freeze
  bug in docs/low-power.md -- that was the RP2350's internal RTC misbehaving
  while the board is powered and running; an external RTC module only
  helps across an actual power-loss, which no internal-RTC fix (lightsleep
  or otherwise) can address regardless.

- UPS (uninterruptible power supply) module for seamless switchover on
  power loss -- e.g. a small LiPo + charge/boost circuit (many off-the-shelf
  "UPS HAT" style boards for this exist) that keeps the Pico continuously
  powered through a mains/USB outage instead of just recovering gracefully
  after one. Stronger than the RTC-module idea above or flash-persisted
  alarm settings: those two help the clock come back correctly after an
  outage, a UPS keeps it actually running (alarm still fires, display still
  updates) *through* one. The three ideas are complementary, not
  alternatives -- a real "keeps working no matter what" clock would
  plausibly want all three eventually.

- Snooze button. Right now any press during MODE_RINGING just dismisses
  (alarm.stop_ringing() in main.py); there's no separate "quiet for N
  minutes then ring again" path.

- Display contrast/orientation flip. Useful if the case ends up mounted
  upside-down or at an angle; picographics likely has a rotate/flip call --
  check the picographics reference in docs/.

- Weekday-only / weekend-skip alarm toggle. alarm.py's Alarm already has an
  enabled flag (long-press C) -- this would extend that to a per-weekday
  mask instead of a single on/off.

- Persist alarm settings (hour/minute/enabled) across reboot/power-loss.
  No extra hardware needed -- the Pico's onboard flash already hosts the
  filesystem; write a small state file on actual change (exit_edit,
  toggle_enabled), read it back at boot with a fallback to config defaults
  if missing/corrupt. See todo.txt's state-machine gap review, gap #2, for
  the full writeup (currently a crash/power-cycle silently resets the
  alarm to config.DEFAULT_ALARM_HOUR/MINUTE with no indication).

- Real CPU-idle power savings during MODE_CLOCK, done properly this time.
  time.sleep_ms() (see docs/low-power.md) doesn't halt the CPU the way
  machine.lightsleep() would have -- that idea got dropped because
  lightsleep() turned out to freeze machine.RTC() outright, a correctness
  bug, not a missed optimization. A real fix would maintain the clock as a
  software value (an RTC snapshot + a time.ticks_ms() reference taken at
  each successful sync, confirmed lightsleep-safe, with "now" computed from
  the ticks_ms() delta) instead of reading machine.RTC() during normal
  operation, which would let lightsleep() come back safely for the idle
  tick. Real effort, not attempted -- see docs/low-power.md's closing
  section.

- Multiple alarms. Current design is a single Alarm instance
  (hour/minute/enabled); supporting several would mean a list of them, a
  way to pick/cycle which one you're editing (current UI only has A/B/C,
  already fully spoken for -- would need a new interaction, e.g. long-hold
  A or a dedicated "next alarm" gesture), and check_ring()/MODE_PREVIEW
  logic extended to loop over all enabled ones instead of assuming one.
  Ties into the reboot-persistence idea below -- would want to save/load
  the whole list, not just one hour/minute/enabled triple.

- Debounce hardening. main.py's poll_button() is simple edge-polling, fine
  for the tactile switches on the Inky Pack, but worth a real debounce
  (e.g. requiring N consecutive stable reads) if double-triggers ever show
  up in practice.

- Dark mode (white-on-black instead of black-on-white). Note: this is
  purely an aesthetic/contrast-preference toggle, not a "visible in the
  dark" feature -- the Inky Pack's e-paper is reflective, not backlit, so
  neither color scheme is readable without ambient light in a dark room.
  If actual dark-room visibility is wanted, that needs a real light source
  (e.g. a physical front-light strip, or timing the clock to briefly flash
  the buzzer/an added LED on a button press) -- unrelated to display.py's
  pen colors.

- Sleep schedule tracker: log "time in bed" (some detectable start event --
  maybe a light/motion sensor, or just "alarm was set"/last-button-press-
  before-morning) through "time alarm dismissed" each night, sent somewhere
  off-device (a small server / cloud endpoint) so trends are visible over
  time instead of living only in the Pico's own limited storage. Needs:
  a defined "went to bed" signal (the tricky part -- the clock only really
  knows when the *alarm* starts and stops, not when you actually lay down),
  a server/endpoint to POST to (could piggyback on the same Wi-Fi connect
  wifi.py already does for time sync), and local buffering for the (fairly
  likely) case the server or Wi-Fi is unreachable right when the alarm gets
  dismissed.
